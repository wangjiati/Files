# 特色功能演示录制流水线（Feature Demo Recording Pipeline）设计

日期：2026-11-07
状态：待用户批准
范围：v1 只覆盖「批量重命名 — 旅行照片」一条演示片，架构需支持后续继续加功能脚本

## 1. 意图与背景

要给 Files 的特色功能做宣传短视频，一条视频讲一个功能点，投放 B 站、小红书、抖音。手工录屏的问题很具体：

- 每次录之前都要手工摆环境（窗口位置、测试文件、主题），找不回来就重来
- 改一句台词就要重录，重录出来的画面和上一版对不上
- 字幕要事后一句句对轴，容易错位

所以把「演示」变成可执行、可版本化的东西：脚本演、机器录、时间点在脚本里打标记。脚本改了随时重录，环境每次都一样，字幕从标记里长出来。

## 2. 目标 / 非目标 / 反目标

### 目标（v1）

- 一个演示运行器，按场景文件驱动 Files 走完「批量重命名照片」的完整操作
- 一次运行产出四件套：
  - `master.mp4`：1920×1080、16:9、60fps、近无损中间母版
  - `master.h265.mp4`：H.265 成片母版
  - `captions.srt`：与画面绑定、可直接导入剪辑软件的字幕
  - `voiceover.txt`：与 SRT 同源同序的配音原文稿
- 可复现：同一场景连跑两次，字幕时间轴偏差 < 150ms，画面内容一致
- 演示素材程序生成、固定种子、可随时重建，不进仓库当二进制
- 环境由「快照 + 准备脚本」保证，一条命令从快照跑到出片

### 非目标（v1 明确不做）

- 自动剪辑、自动排版、平台适配成片（后期在剪映里做）
- 竖屏版本
- 第二条功能脚本（但架构必须允许后加）
- 音轨、TTS、配音合成
- 多语言文案

### 反目标（做了就算失败）

- 为了好录而在产品里加「演示模式」开关，或改产品 UI 外观
- 用截图合成、动画替代真实操作
- 用固定 `sleep` 硬编码等待（必须等可见状态）
- 让脚本依赖中文控件文案（改一句文案视频脚本就断）

## 3. 已定的约束（用户决定）

| 项 | 决定 |
| --- | --- |
| 画面比例 | 横屏 16:9，1920×1080 |
| 编码 | H.265 / 60fps |
| 投放 | B 站、小红书、抖音（平台自适应，不做裁切版本） |
| 后期 | 用户用剪映手动合成，自动剪辑不在本轮 |
| 一次性产出 | 视频 + 字幕 + 配音原文稿同时生成 |
| 运行环境 | 沙盒优先，不好操作就用虚拟机 |
| 演示照片 | 程序生成，录屏不放大看图 |
| 文案语气 | 简明扼要讲解，极少情绪、极少口气 |
| 演示题材 | 批量重命名，旅行照片管理场景 |

## 4. 方案

### 4.1 组成

| 部件 | 位置 | 职责 |
| --- | --- | --- |
| 演示运行器 | `tests/Files.DemoRecording`（.NET 控制台） | 读场景，驱动 UI，写标记 |
| 场景文件 | `tests/Files.DemoRecording/Scenarios/*.json` | 步骤序列 + 每步文案 |
| 素材生成 | `tools/DemoAssets/New-DemoPhotoSet.ps1` | 生成固定照片集与初始乱名 |
| 录制编排 | `tools/DemoAssets/Invoke-DemoRecording.ps1` | 一条命令跑完：备素材 → 起 Appium → 开录 → 跑场景 → 停录 → 转码 → 生成字幕 |
| 环境准备 | `tools/DemoVm/*.ps1` | 造快照机、装包、固定桌面 |

技术栈复用现有 `tests/Files.InteractionTests` 的 Appium + Windows Driver 方案（仓库已有依赖与启动逻辑），不引入新的 UI 自动化框架。

### 4.2 步骤模型

场景是一串步骤，每步可以带一句文案：

```
{ id, action, target, value, settle, caption?, hold? }
```

- `action`：`launch` / `click` / `key` / `type` / `anyClick` / `waitFor` / `pause` / `marker`
- `target`：定位方式，优先 `automationId`，其次 `name`，最后 `activeWindowPath`（见 4.4）
- `settle`：等待的可见状态（元素出现/消失/可交互/预览文本变化），不是固定时长
- `caption`：这句台词原文，同时用于 SRT 与配音稿
- `hold`：这句台词至少停留多久（默认由字数估算，仅在需要时覆盖）

步骤开始/结束时写入标记。标记文件是整条流水线唯一的对齐依据。

### 4.3 时间对齐

- 全局只有一个 `Stopwatch`，录制确认开始后启动，所有标记取它的 elapsed
- 录制开始的判定不能靠猜：读 ffmpeg 的 stderr，拿到实际开始采集的信号后才启动时钟
- 标记 → `timeline.json`（毫秒级），再由它生成 `.srt` 与 `voiceover.txt`
- 误差预算：采集启动延迟（已由上面的握手消除） + 点击到界面响应（由 `settle` 吸收） + 编码帧对齐（≤16.7ms）

### 4.4 输入与可见光标（关键约束）

**Appium 的 `Click()` 走 UI Automation 的 Invoke，不移动物理光标**，所以录出来看不到鼠标，点击像是凭空发生的——这对宣传片是硬伤。

因此运行器要把「找」和「点」分开：

- 找：用 Appium/UIA 拿到目标控件的屏幕矩形与中心点
- 点：`SetCursorPos` + `SendInput` 产生真实输入，并先走一段 ~120ms 的插值移动，让画面像手在移

同理，键盘操作走真实按键注入，不走 UIA 的 Value 赋值。

这条约束反过来要求控件**可稳定定位**：全仓库目前只有 4 个 `AutomationId`，批量重命名又是个 overlay（`BatchRenameOverlayPresenter`），现有测试靠 Name 文本找控件。v1 需要给录制路径上的控件补一小组 `AutomationId`——这是产品代码改动，保持最小集，只加录制会走的那些。

### 4.5 录制与编码（两段式）

| 阶段 | 工具 | 目的 |
| --- | --- | --- |
| 采集 | ffmpeg `gdigrab`，60fps，`libx264 -preset ultrafast`，高码率近无损 | 实时不占 CPU，保证不掉帧 |
| 转码 | ffmpeg `libx265`，1080p60，`crf` 18–20，`yuv420p`，bt709，`+faststart` | 出 H.265 成片母版 |

- 不用 `ddagrab`：它依赖 DXGI 桌面复制，虚拟机里不可靠
- 60fps 的前提是显示输出真的是 60Hz：虚拟机固定 1920×1080 / 60Hz、缩放 100%、关闭动态刷新
- 采集与转码拆开，是这套方案能在无 GPU 的虚拟机里成立的核心

### 4.6 运行环境

- Hyper-V 虚拟机（Gen2，4 核起步，8 核更好），基线快照 `demo-base`
- 基线内装好：Files 包、FFmpeg、Appium/WinAppDriver、生成好的照片集
- 基线固定：分辨率与刷新率、缩放、主题（浅色）、关闭通知与专注助手、Files 窗口初始位置与尺寸
- 每次录制：恢复快照 → 跑 `Invoke-DemoRecording.ps1`
- 首次启动 app 较慢，编排脚本里包含一次「预热启动（不录）」，避免片头出现加载画面

### 4.7 产出物

```
out/batch-rename/<yyyyMMdd-HHmmss>/
  master.mp4          # 近无损中间母版
  master.h265.mp4     # H.265 母版
  captions.srt        # 字幕
  voiceover.txt       # 配音原文稿（一句一行，带时间）
  timeline.json       # 标记与步骤记录，排查用
```

## 5. v1 演示脚本草案（批量重命名 · 旅行照片）

素材：24 张程序生成的城市/风景照，文件名故意是相机导出风格（`IMG_20240312_104512.jpg` 这类），尺寸统一。

| # | 画面 | 台词（草案，语气冷静） |
| --- | --- | --- |
| 1 | 打开照片文件夹，网格视图 | 相机导入的照片，文件名通常只是一串编号。 |
| 2 | 全选 | 这些照片要按地点和时间重新整理。 |
| 3 | F2 打开批量重命名 | 选中后按 F2，打开批量重命名。 |
| 4 | 填规则（地点 + 日期 + 序号） | 一条规则，先把命名方案定下来。 |
| 5 | 预览列表逐行变化 | 预览会实时显示改后的名字。 |
| 6 | 确认 | 确认后整批生效。 |
| 7 | 回到文件夹，文件名已整齐 | 上百张照片，一次改完。 |

台词在实现阶段可继续打磨，结构和时长以场景文件为准。

## 6. 风险与未知

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| WinAppDriver 在新版 Windows 上不稳 | 找不到控件、会话掉线 | 定位层可替换为 FlaUI，输入层不动；先做 spike 验证 |
| 虚拟机内 WinUI 动画实际不足 60fps | 60fps 只体现在容器上，画面仍旧顿 | 开工第一件事：录 10 秒滚动列表，数重复帧 |
| `gdigrab` 时间戳漂移 | 字幕整体偏 | 用 `timeline.json` 事后核对；必要时改用帧计数换算 |
| 补 `AutomationId` 属产品改动 | 影响产品代码 | 只加录制路径的最小集，独立提交 |
| 快照恢复后首次启动慢 | 片头有加载态 | 编排脚本预热启动 |

## 7. 留给建造者的决定

- 运行器的类结构与场景文件的字段命名
- 字幕样式与位置（母版不烧字幕，样式在剪映里定）
- 鼠标移动曲线与点击前后的停顿参数
- ffmpeg 的 preset / crf 具体取值
- 图片生成的具体画法（只要缩略图下像照片、可复现即可）

## 8. 验收

- 一条命令从快照跑到出片，产出 4.7 中的五个文件
- 连跑两次：字幕时间轴偏差 < 150ms；画面内容一致（抽帧对比）
- `master.h265.mp4` 为 1920×1080 / 60fps / HEVC
- `voiceover.txt` 与 `captions.srt` 逐行文案一致
- 人工看片：无卡顿、无加载态、光标准确落在被点的控件上、字幕与动作对得上
