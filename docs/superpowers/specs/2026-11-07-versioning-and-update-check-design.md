# Files 内部分支：子版本号与更新检查设计

日期：2026-11-07
状态：待批准
相关上游：`files-community/Files`
本分支仓库：`wangjiati/Files`

## 1. 意图与背景

当前应用版本固定为 `4.3.1.0`，与上游同号：

- 用户和发布记录无法区分"这是上游 4.3.1"还是"我们基于 4.3.1 的第几次内部发布"。
- 用户不知道是否已有新版，只能靠人工通知或自己去仓库看。
- 本分支面向个位数用户，没有服务器、没有遥测、没有自动更新基础设施。

本设计要解决两件事：

1. 建立一套能同时表达**上游版本**和**复刻迭代**的版本号。
2. 提供一个**每日一次、可关闭、不采集遥测**的更新检查，发现新版时提示用户并可跳转下载。

## 2. 目标、非目标与反目标

### 2.1 目标

- 四段版本号同时承载上游版本和内部迭代号。
- 设置页和更新弹窗都同时显示"上游版本"和"内部迭代"。
- 启动时每日最多检查一次 GitHub Releases；发现新版弹窗展示本版变化。
- 用户可选择"下载更新"或"以后再说"；选择后该版本不再主动提醒。
- 设置中可关闭更新检查，也可手动"立即检查"。
- MSIX 与便携版都生效，不引入服务器、不采集用户标识。
- 发布流程能产出可被客户端解析的 Release（本版可手工发布，但格式固定）。

### 2.2 非目标

- 不实现自动下载、静默安装或差量更新。
- 不做用户统计、遥测、设备指纹或使用行为上报。
- 不做强制更新、灰度发布、多通道（beta/stable）切换。
- 不接入 Microsoft Store 或 Files 官方更新源。
- 本版不做 Gitee 镜像和双源自动切换；预留后续替换更新源的能力即可。
- 不新增 Markdown 渲染控件或第三方更新 SDK。

### 2.3 反目标（技术上可行也算失败）

- 启动被网络请求阻塞，或离线时弹出错误。
- 每天反复弹同一个版本，或在用户关闭后仍然联网检查。
- 为了统计用户而加入任何形式的客户端遥测。
- 更新提示引导用户下载未经校验的可执行文件。
- 破坏便携版的自包含与可迁移特性。

## 3. 已确认的产品决定

- 更新源先用 GitHub，用户规模上来后再重新规划。
- 支持渠道是飞书群；仓库 Issues/Discussions 当前关闭。
- 每日只检查一次；启动时检查。
- 发现更新弹窗展示更新内容，用户可选"下载更新"或"以后再说"。
- "以后再说"表示**这个版本不再提醒**，直到出现更新版本；同时保留手动检查入口。
- 设置中可关闭检查更新。
- 内部迭代号在合并上游版本后从 1 重新计数。

## 4. 版本号方案

### 4.1 格式

版本号保持四段纯数字：

```text
<upstreamMajor>.<upstreamMinor>.<upstreamBuild>.<forkIteration>
```

示例：

| 含义 | 版本 |
| --- | --- |
| 基于上游 4.3.1 的第 7 次内部发布 | `4.3.1.7` |
| 上游升级到 4.4.0 后首次内部发布 | `4.4.0.1` |

规则：

- 前三段等于同步到的上游版本；每次同步上游时更新。
- 第四段是内部迭代号，每次内部发布 +1；同步上游后重置为 1。
- 四段都必须 ≤ 65535，主版本不能为 0（MSIX 约束）。
- 如果上游出现非零的第四段，内部迭代号仍占用第四段；上游完整版本记录在 `RELEASE-INFO.txt` 中，界面只展示前三段。
- 第一个采用新方案的版本是 `4.3.1.1`；`Version.props` 保存**本次构建要产出的版本**，不是上次已发布的版本。

### 4.2 各处的版本表示

- 包版本 / 程序集版本 / 文件版本：`4.3.1.7`。
- `InformationalVersion`：`4.3.1+fork.7`，出现在 exe 文件属性中。若 SDK 自动追加源码提交号，需要为应用项目关闭该行为，保持可读。
- 界面显示：`版本 4.3.1（内部迭代 7）`。
- 补充信息：`基于上游 4.3.1`。
- 构建提交和上游提交不进入运行时 UI，保留在 `RELEASE-INFO.txt` 和 Release 页面中；后续需要时再通过 `AssemblyMetadata` 注入。
- 更新说明和 Release 标题使用 `4.3.1.7`。

### 4.3 单一事实源

新增 `eng/Version.props`：

```xml
<Project>
  <PropertyGroup>
    <UpstreamVersion>4.3.1</UpstreamVersion>
    <ForkIteration>1</ForkIteration>
  </PropertyGroup>
</Project>
```

- `src/Files.App/Files.App.csproj` 导入该文件，计算 `Version`、`AssemblyVersion`、`FileVersion`、`InformationalVersion`。
- `Package.appxmanifest` 的 `Identity Version` 必须与计算结果一致。
- 提供一个小的版本更新脚本（例如 `eng/Set-AppVersion.ps1`）同时更新 `Version.props` 和清单，避免手改两处。
- 发布脚本继续校验清单、程序集和便携 exe 三者版本一致；不一致直接失败。
- 发布脚本可选地校验当前版本大于最近的 `v*` 标签，防止漏改版本号。
- 同步上游的清单步骤中必须包含：更新 `UpstreamVersion`、把 `ForkIteration` 设为 1、记录上游提交。

### 4.4 运行时读取

- MSIX：沿用包版本。
- 便携版：沿用程序集版本。
- 两者都必须得到同一个四段版本；`AppRuntime.Current.Version` 保持不变。
- 上游版本和内部迭代号从版本号拆解即可，不额外持久化。

## 5. 更新检查

### 5.1 数据来源

直接读取 GitHub Releases，不额外维护 JSON 文件：

```text
GET https://api.github.com/repos/wangjiati/Files/releases/latest
Accept: application/vnd.github+json
User-Agent: Files-Internal/<version>
```

默认不加认证。仓库必须保持公开。

用到的字段：

- `tag_name`、`name`：解析版本号，容忍 `-portable` 等历史后缀。
- `body`：更新说明。
- `html_url`：完整说明与下载页。
- `published_at`：发布日期。
- `assets[]`：文件名、大小、`digest`（`sha256:...`）、下载地址。

版本解析规则：

- 用正则从 `tag_name` 提取 `v?(\d+(?:\.\d+){2,3})`。
- 不足四段时补 0。
- 解析失败视为没有可用更新，不报错。

### 5.2 检查时机与频率

- 启动流程中，主窗口和会话加载完成后异步触发，不阻塞 UI。
- 仅在 Release 构建执行（`#if !DEBUG`），避免开发构建产生网络噪声。
  不能使用 `AppEnvironment` 判断：内部发布不经过 `Configure-AppxManifest.ps1`，运行时仍是 `Dev`。
- 手动"立即检查"在所有构建可用。
- 每日最多一次：以本地日期为单位记录"最后检查日期"，同一天再次启动直接跳过。
- 检查失败也记录当天已尝试，避免离线时每次启动都发请求。
- 用户关闭"检查更新"后完全不发起请求。

### 5.3 判定逻辑

按以下顺序：

1. 开关关闭 → 不检查。
2. 今天已检查过 → 不检查。
3. 拉取 Release 失败 → 静默结束，记录当天已尝试。
4. 解析出的版本 ≤ 当前版本 → 无更新。
5. 解析出的版本等于用户跳过的版本 → 无弹窗（工具栏状态可保留）。
6. 否则 → 标记有新版本，记录可用版本、说明、发布页地址、目标资产。

比较使用 `System.Version`，不做字符串比较。

### 5.4 资产选择

- 根据当前分发方式选择资产：
  - MSIX 版：优先匹配 `.msix`，其次 `.msixbundle`。
  - 便携版：匹配 `-portable.zip`。
  - 架构按当前进程架构匹配 x64 / arm64；匹配不到时回退到发布页。
- 不自动下载；"下载更新"打开 Release 页面，由用户选择并手动安装。
- 如果 Release 提供 `digest`，在下载页说明中展示 SHA-256；没有则读取 `SHA256SUMS.txt` 资产。

### 5.5 失败与限流

- 超时 5 秒，不重试。
- 网络错误、403、429、5xx、JSON 解析失败、字段缺失都按"本次无结果"处理。
- 仅在调试日志中记录原因，不弹窗、不写用户可见错误。
- 条件请求可选：保存 `ETag`，下次带 `If-None-Match`；304 不计入 GitHub 匿名配额。

## 6. 用户体验

### 6.1 启动更新弹窗

触发：满足 5.3 第 6 条。

内容：

- 标题：`发现新版本 4.3.1.7`
- 副标题：`基于上游 4.3.1 · 内部迭代 7`
- 更新说明摘要：从 `body` 中提取 `## 本版变化` 小节，最多显示约 10 条或 1200 字符；超出时提示查看完整说明。
- 主要按钮：`下载更新` → 用默认浏览器打开 `html_url`。
- 次要按钮：`以后再说` → 记录该版本为已跳过并关闭。
- 可选链接：`查看完整更新说明` → 同样打开 `html_url`。

实现要求：

- 弹窗在 UI 线程显示，且只显示一次。
- 用户正在启动恢复会话时不打断；等启动标签页稳定后再弹。
- 关闭弹窗不等于跳过版本；只有"以后再说"才记录跳过。

### 6.2 设置页

位置：设置 → 关于，沿用现有版本卡片。

- 版本卡片描述改为：`版本 4.3.1（内部迭代 7）`，并补充一行 `基于上游 4.3.1`。
- 新增"更新"设置卡片：
  - 开关：`启动时检查更新`（默认开启）。
  - 按钮：`立即检查`。
  - 状态文本：`今天已检查` / `已是最新版本` / `发现新版本 4.3.1.7` / `检查失败，稍后再试` / `已跳过 4.3.1.7`。
- 手动检查忽略"每天一次"限制；总开关关闭时禁用按钮并说明原因，此时不发起任何请求。

### 6.3 工具栏

现有工具栏更新按钮绑定 `IUpdateService.IsUpdateAvailable`，继续复用：

- 发现新版本时显示更新图标。
- 点击打开 Release 页面。
- 用户跳过的版本不弹窗，但工具栏仍可保留入口。

## 7. 设置与状态持久化

- `启动时检查更新`：加入 `IApplicationSettingsService`，默认 `true`。
- `SkippedVersion`：加入 `IApplicationSettingsService`，默认空。
- `LastUpdateCheckDate`、`ETag`：属于本机运行状态，写入 `ILocalStateStore`；便携版落到 `Data` 目录，MSIX 走现有本地状态实现。
- 不新增除现有本地状态存储之外的持久化位置，也不引入云同步。

## 8. 安全与隐私

- 只访问 `https://api.github.com`，不携带用户标识、机器名、路径或使用数据。
- `User-Agent` 仅包含产品名和版本号。
- 不自动执行下载内容；不自动安装。
- 更新说明和资产地址按不可信输入处理：只作为文本展示和 URL 打开，不拼接进命令或脚本。
- 打开链接前校验协议为 `https`，主机为 `github.com`。
- 发布侧继续提供 `SHA256SUMS.txt`，并在 Release 说明中展示校验值。

## 9. 发布流程改动

本版**不新增**自动创建 Release 的脚本或工作流。Release 由维护者手工创建（可用 `gh release create`），`Build-Internal.ps1` 继续负责版本校验和产物生成。

- Release 标签统一为 `v<四段版本>`，例如 `v4.3.1.7`；不再把分发方式写进标签。
- Release 标题：`Files Internal 4.3.1.7`。
- Release 正文保留固定小节：版本、平台、上游基线、构建提交、本版变化、包内容、安装、校验。
- `## 本版变化` 由维护者手工填写，是客户端弹窗和发布页的共同来源。
- 上传资产：MSIX、便携 ZIP、`SHA256SUMS.txt`、`RELEASE-INFO.txt`。
- 预发布构建标记为 `prerelease`，避免被 `releases/latest` 选中。
- 发布前先把 `Version.props` 设为本次要发布的版本并提交，再打包，保证 `RELEASE-INFO.txt` 记录正确版本。
- 当前最近一次发布是 `4.3.1.0`，所以第一次使用新格式的发布是 `4.3.1.1`。
- 清理 `Constants.ReleaseNotesUrl` 对 `files.community` 的依赖：要么删除未使用的发布说明入口，要么指向本分支 Release 页。

## 10. 测试

### 10.1 单元测试

- 版本解析：`v4.3.1.7`、`4.3.1`、`v4.3.1.7-portable`、非法标签。
- 版本比较：`4.3.1.7 < 4.4.0.1`，相等版本不算更新。
- 每日限制：同一天第二次检查跳过；跨天恢复。
- 跳过逻辑：跳过当前版本后不弹窗；出现更高版本后恢复提示。
- 总开关：关闭后不发起请求。
- 资产选择：MSIX、便携版、架构不匹配时的回退。
- 说明摘要：从 Markdown 中提取"本版变化"，超长截断。
- HTTP 失败：超时、403、429、5xx、非法 JSON 均静默结束。

### 10.2 手工验证

- MSIX 与便携版分别启动，确认版本显示和检查行为一致。
- Release 构建会检查更新，Debug 构建不会自动检查，但手动检查可用。
- 断网启动：不卡顿、不报错，当天不再重复请求。
- 关闭开关后确认无网络请求。
- 手动"立即检查"在开关开启时可绕过每日限制。
- 设置"以后再说"后，同日和次日启动都不再弹同一版本。
- 下载按钮打开正确的 Release 页面。

### 10.3 构建验证

- `msbuild -restore src/Files.App/Files.App.csproj -p:Configuration=Debug -p:Platform=x64`
- 按项目要求运行 `.github/scripts/Build-Internal.ps1` 产出发布包，并启动打包版本做 UI 冒烟。

## 11. 建造者可自行决定

- 更新服务与设置的具体命名、接口拆分方式。
- 弹窗和设置卡片的 XAML 布局与措辞。
- 说明摘要的截断长度和具体清洗规则。
- 版本更新脚本的实现方式，以及是否把 `eng/Version.props` 纳入构建校验。
- GitHub 条件请求与 ETag 是否本版实现。
- 是否保留 `ManualUpdateService` 作为无网络环境的空实现。

## 12. 未决问题
